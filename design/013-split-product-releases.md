# 三个业务各自发布

## 1. 背景与目标

- 当前问题：页面镜像、引擎镜像和客户端安装包虽然分三个工作流，但都挂在同一个 `vX.Y.Z` 上。Release 标题都是这个标签，说明也是同一篇，用户看不出这一条发布的是页面、引擎还是安装包。版本还必须事先推好，并且三个业务只能共用一个号。
- 目标用户与场景：维护者按改动范围单独发布。下载安装包的人、拉取页面镜像的人、拉取引擎镜像的人，在发布列表里能直接看出这条发布是什么。三个业务以后可以各自递增版本；仓库仍先保持一个。
- 成功标准：从选中的提交填写版本号即可发布。成功后创建 `web-vX.Y.Z`、`engine-vX.Y.Z` 或 `client-vX.Y.Z`，并各写一条标题不同的 Release。页面 `0.3.0`、引擎 `0.2.1`、客户端 `0.4.0` 可以同时存在。镜像上的 `latest` 只和本业务的标签比较。
- 非目标：现在不拆成三个仓库。不改镜像坐标里的版本格式，`ghcr.io/<所有者>/tucools-web:0.3.0` 仍不带 `web-v` 前缀。不迁移已经发出的 `vX.Y.Z` 和 `models`。不在推送标签时自动构建。

## 2. 现状与约束

- 同一份 `apps/web` 给 Docker 和安装包使用。镜像定义在 `deploy/Dockerfile.web` 和 `deploy/Dockerfile.engine`。安装包配置在 `apps/desktop/package.json`。
- 版本页在安装包里对照客户端发布，在网页和 Docker 里对照页面发布。模型包发布仍使用 `models`。
- GitHub 一个仓库只有一个 Latest。客户端在本业务没有更高版本时占用它，页面和引擎不占用。Docker 镜像的 `latest` 标签按镜像分开。
- 工作流使用 `GITHUB_TOKEN` 创建标签和 Release。不移动已经指向其他提交的标签。

## 3. 方案概览

维护者在 Actions 里选择提交并填写 `X.Y.Z`。工作流校验版本号，构建成功后再把 `业务-vX.Y.Z` 打到这次提交。标签不存在就创建；已经指向这次提交就继续上传；指向别的提交就失败。

三个入口仍是 `workflow_dispatch`。页面和引擎共用内部镜像构建。客户端仍是一个入口、三个互不依赖的平台任务。谁先成功，谁就创建本业务的 Release；同一次客户端发布里，后完成的平台只追加附件。

## 4. 详细设计

### 4.1 数据模型与权威来源

- 版本号来自本次填写的 `X.Y.Z`。`vX.Y.Z` 以及和当前业务一致的 `web-vX.Y.Z` 也可以填，脚本会收成三位版本号。
- git 标签是 `web-vX.Y.Z`、`engine-vX.Y.Z`、`client-vX.Y.Z`。
- Release 标题是 `TuCools Web X.Y.Z · 页面镜像`、`TuCools Engine X.Y.Z · 引擎镜像`、`TuCools Client X.Y.Z · 客户端安装包`。说明分别来自 `release-notes-web.md`、`release-notes-engine.md`、`release-notes-client.md`。
- 镜像名仍是 `ghcr.io/<所有者>/tucools-web` 和 `ghcr.io/<所有者>/tucools-engine`，标签是不带前缀的版本号。
- `latest` 的表单仍是 `auto`、`always`、`never`。`auto` 只查询本业务前缀。

### 4.2 API、权限与错误语义

- 版本为空、不是三位数字、业务前缀和当前工作流不一致：任务失败并写明原因。
- 创建标签时远程暂时不可确认：任务失败，不假设标签不存在。
- 镜像推送后的描述检查保持原样。
- 版本页请求 `releases/tags/web-vX.Y.Z` 或 `releases/tags/client-vX.Y.Z`。发布列表里只比较同一前缀，草稿、预发布、`models` 和旧的 `vX.Y.Z` 不参与。

### 4.3 状态、缓存、并发与幂等

- 并发组仍按产物和版本分开。
- 客户端三个平台可能同时创建同一个标签和同一条 Release。先推成功的标签保留；后到的任务确认标签指向同一提交后继续。Release 已存在时保留第一份说明。
- 重复上传仍使用 `gh release upload --clobber`。
- 构建失败时还不创建标签，同一个版本号可以在修好后的新提交上再发。构建已经成功并打上标签后，要换提交就换版本号。

### 4.4 到 4.6

不新增界面文案。版本页仍用原来的句子，比较对象改为当前运行位置对应的业务。手动运行限于有仓库写权限的人。脚本不打印 `GH_TOKEN`。

## 5. 失败与恢复

- 某个平台或某个镜像失败时，其他任务继续。失败发生在打标签之前时，用同一个版本号重跑即可。
- 标签已经指向别的提交时，停止并更换版本号。
- 页面或引擎发布成功后，仓库 Latest 仍留在最新的客户端发布上。下载安装包的人从标题以 `TuCools Client` 开头的条目进入；如果客户端已经是本业务最高版本，也可以走 Releases 的 Latest。

## 6. 兼容与数据处理

- 已发出的 `vX.Y.Z`、`models` 和已有镜像标签保持不动。
- 新的版本页不再把旧的 `vX.Y.Z` 当成页面或客户端更新。已经安装的旧客户端要等第一条 `client-v*` 发布后，才能在版本页看到新的客户端版本。
- Compose 的 `TUCOOLS_VERSION` 仍同时作用于两个镜像。两个版本不同时，分别设置 `TUCOOLS_WEB_IMAGE` 和 `TUCOOLS_ENGINE_IMAGE`。
- 不涉及数据库。

## 7. 实施顺序

1. 版本脚本改为生成业务标签，并在构建成功后创建标签和独立 Release。
2. 三个工作流改为必填版本号。客户端工作流在 Actions 里显示为「发布客户端」。
3. 版本页按 `web` 或 `client` 比较。部署说明、README 和开发说明改成新的发布步骤。

## 8. 验证与验收

- 脚本语法、版本号样例、同一业务的更高标签判断、说明模板替换、Release 标题和 `--latest` 参数、版本页比较。
- 未在 GitHub Actions 上实际构建镜像或安装包，未向 GitHub 推送标签。

## 9. 风险与待决策

| 项目 | 影响 | 建议 | 决策状态 |
| --- | --- | --- | --- |
| 一个仓库只有一个 Latest | 页面或引擎若占用它，下载按钮会离开安装包 | 客户端在本业务最高时占用 Latest，另外两条用标题区分 | 已实施 |
| 旧的 `vX.Y.Z` 不再参与版本检查 | 旧客户端在第一条 `client-v*` 出现前，版本页显示没有可比较的版本 | 下一次客户端发布后恢复比较 | 已实施 |
| 仓库规则禁止 Actions 创建标签 | 构建成功后的打标签步骤失败 | 需要仓库允许 `GITHUB_TOKEN` 写入标签 | 待第一次真实发布确认 |
